# [Min beste venn](https://nnsc.tf/challenges?challenge=forensics_Min+beste+venn)

**Description:** Signal wasn't secure enough so we moved to something else. I heard about something called chatflare, and it seemed interesting.

## 1. Initial triage

Start by identifying what's actually inside the capture.

```bash
file capture.pcap
tshar -r capture.pcap -q -z io,phs
```

**Results:**

```
capture.pcap: pcap capture file, microsecond ts (little-endian) - version 2.4 (Ethernet, capture length 262144)

===================================================================
Protocol Hierarchy Statistics
Filter:

frame                                    frames:3662 bytes:805277
  eth                                    frames:3662 bytes:805277
    ip                                   frames:3662 bytes:805277
      tcp                                frames:3662 bytes:805277
        http                             frames:2270 bytes:712893
===================================================================
```

The protocol hierarchy shows the entire capture is plain HTTP over TCP, about 3600 frames, no TLS, no DNS. That means everything we need is readable in cleartext, which is a strong hint that the challenge is about traffic analysis rather than decryption.

## 2. Look at what's being requested

```bash
tshark -r capture.pcap -Y http.request -T fields -e frame.number -e http.host -e http.request.method -e http.request.uri
```

Every single request is:

- Method: `HEAD`
- Host: `static.notion-static.com`
- Path pattern: `/cf<big number>/h/s<number>.css` or `/cf<big number>/d/{h,c}/{0,1}/<number>.css`

Two things stand out immediately:

1. There is no `User-Agent` header, only `accept` and `host`. A real browser never does this. This traffic was generated by a custom script, not a browser.
2. There are over a thousand requests for what look like tiny CSS fragments, all HEAD requests, to a domain designed to look like Notion's real static asset CDN.

Check the responses:

```bash
tshark -r capture.pcap -Y http.response -T fields -e http.response.code | sort | uniq -c
```

**Results:**

```
1135 404
```

Every single response is `404 Not Found`. None of these files exist. So the requests themselves aren't fetching real content, they exist purely to _be sent_. That's the signature of a covert channel.

## 3. Find the bit the server is leaking back

Since the response body is empty, any hidden signal has to be in something else the server returns. Dump full response headers for one request:

```bash
tshark -r capture.pcap -Y "tcp.stream==0 && http.response" -V
```

Headers include a Cloudflare-specific one:

```
cf-cache-status: MISS
```

Check the distribution of this header across the whole capture:

```bash
tshark -r capture.pcap -Y http.response -T fields -e "http.response.line" | grep -io "cf-cache-status: [A-Z]*" | sort | uniq -c
```

Result: 755 `MISS`, 380 `HIT`. That's the leak. `cf-cache-status` tells you whether Cloudflare had already cached that exact URL. If a URL is requested once, it's a MISS. If the same URL is requested again, it's a HIT. So whether a given URL gets requested **once or twice** is a controllable, observable 1-bit signal, and that's exactly what the attacker used to smuggle data out.

Save the request timestamps and URIs to a file, and separately map every response back to the frame number of the request that caused it, along with its cache status:

```bash
tshark -r capture.pcap -Y http.request -T fields -e frame.time_relative -e http.request.uri > /tmp/reqs.txt

tshark -r capture.pcap -Y http.request -T fields -e frame.number -e http.request.uri > /tmp/req_uri.txt

tshark -r capture.pcap -Y http.response -T fields -e frame.number -e http.request_in -e "http.response.line" | awk -F'\t' '{status = ($3 ~ /cf-cache-status: HIT/) ? "HIT" : "MISS"; print $2"\t"status}' > /tmp/resp_status.txt
```

Now join the two files by request frame number, group by URI, and check whether every URI requested more than once really does go MISS first, then HIT for every repeat:

```python
uri_of = {}
for line in open('/tmp/req_uri.txt'):
    f, uri = line.strip().split('\t')
    uri_of[int(f)] = uri

from collections import defaultdict
by_uri = defaultdict(list)
for line in open('/tmp/resp_status.txt'):
    req_f, status = line.strip().split('\t')
    req_f = int(req_f)
    by_uri[uri_of[req_f]].append((req_f, status))

dup_count = 0
bad = 0
for uri, hits in by_uri.items():
    if len(hits) > 1:
        dup_count += 1
        hits.sort()
        statuses = [s for _, s in hits]
        if statuses[0] != 'MISS' or any(s != 'HIT' for s in statuses[1:]):
            bad += 1

print(f'{dup_count} URLs were requested more than once')
print(f'{bad} of them broke the MISS-then-HIT pattern')
```

**Results:**

```
380 URLs were requested more than once
0 of them broke the MISS-then-HIT pattern
```

That confirms it: every duplicated URL follows MISS then HIT, with zero exceptions. So the covert channel is: **for each possible "value", request its URL once if the bit is 0, twice if the bit is 1.**

## 4. Decode the URL numbering scheme

Now we need to figure out what "value" each URL path number actually represents. Pull the full set of numbers used under one folder, e.g. `d/h/0/`:

```bash
grep -oP "(?<=/cf1787417395/d/h/0/)[0-9]+(?=\.css)" /tmp/reqs.txt | sort -n -u
```

The result is a strange sequence: `0,1,2,3,4,5,6,7,10,11,...,17,20,...,27,...,150,...,157`. Notice the units digit never goes above 7, it jumps straight from `X7` to `(X+1)0`. That's not decimal counting, it's a byte value split into two parts and each part written as a decimal digit-string:

```
value = (N // 10) * 8 + (N % 10)
```

With this formula the observed numbers `0` through `157` map exactly onto `0` through `127`, the full 7-bit ASCII range. Each `/d/h/0/<N>.css` and `/d/h/1/<N>.css` path is a stand-in for one ASCII byte value, disguised so the URL never contains a literal `8` or `9`.

There are four such folders in the capture: `d/h/0`, `d/h/1`, `d/c/0`, `d/c/1`. Each is an independent channel that maps its own value range onto the same "request once = 0, request twice = 1" bitmap.

## 5. Reconstruct the bitmap and decode it

For each folder, build a 1-bit-per-value array, in increasing value order, then pack every 8 bits into a byte.

```py
import re
from collections import defaultdict

uri_map = {}
for line in open('/tmp/req_uri.txt'):
    f, uri = line.strip().split('\t')
    uri_map[int(f)] = uri

groups = defaultdict(list)
for f, uri in uri_map.items():
    groups[uri].append(f)

cat = defaultdict(dict)
for uri, frames in groups.items():
    m = re.match(r'/cf1787417395/d/(h|c)/(\d)/(\d+)\.css', uri)
    if m:
        t, s, raw = m.group(1), int(m.group(2)), m.group(3)
        n = int(raw)
        value = (n // 10) * 8 + (n % 10)
        cat[(t, s)][value] = cat[(t, s)].get(value, 0) + len(frames)

def bitmap(cnt, maxv):
    return ''.join('1' if cnt.get(v, 0) > 1 else '0' for v in range(maxv + 1))

def to_bytes(bits):
    n = len(bits) // 8 * 8
    return bytes(int(bits[i:i+8], 2) for i in range(0, n, 8))

for key in [('h', 0), ('h', 1), ('c', 0), ('c', 1)]:
    maxv = max(cat[key].keys())
    print(key, to_bytes(bitmap(cat[key], maxv)))
```

**Results:**

```
('h', 0) b'\x0fmin beste venn?'
('h', 1) b'\x0fcan i haz flag?'
('c', 0) b'\x03ja?'
('c', 1) b'6NNS{*_****_********_****_***_*****_****_**_***_******}'
```

Each message is length-prefixed: the first byte is the string length in hex/decimal, and the following bytes are the ASCII payload. `0x0f` = 15, matching `"min beste venn?"`. `0x03` = 3, matching `"ja?"`. `0x36` = 54, matching the length of the flag string that follows it.

## 6. Read off the flag

The `d/c/1` channel decodes directly to the flag, right after its length byte.

The other three channels are flavor text forming a little exchange, consistent with the challenge's chat theme, and confirm the decoding scheme is correct before trusting the flag output.
